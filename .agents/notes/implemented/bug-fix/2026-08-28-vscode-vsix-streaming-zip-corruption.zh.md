# Agent Note：pack-vsix 的流式 zip 损坏条目，已换批量 zipSync 并加自校验

Status: implemented

[English](2026-08-28-vscode-vsix-streaming-zip-corruption.md) | 中文

## 问题

首个携带闭包的 VSIX（约 1.26 万条目）解压不可靠：bsdtar 中途放弃，`unzip -t` 对网页前端 assets 下三个 KaTeX 字体条目报 bad CRC。字节对比证实是归档数据真的坏了——解压出的字节与打包源文件不同——所以损坏发生在写归档时，而不是物化闭包时。`scripts/pack-vsix.mjs` 用 fflate 的流式 `Zip`/`ZipDeflate` 把每个条目同步推进同一个 `Zip` 实例。对同一字体目录、同一模式的 59 条目复现产物干净无错，因此故障是流式状态机内规模或顺序相关的；确切触发点未定位。

## 决策

`pack-vsix.mjs` 改用 fflate 的批量 `zipSync`（一次同步调用打包完整条目表，约 120 MB 闭包输入对应约 200 MB 峰值），并在报告成功前验证产物：`unzipSync` 全量回读归档，任何 CRC 或结构不匹配都会抛错，条目数还会与打包表比对。损坏条目现在会让打包失败，而不是产出一个解不开的 VSIX。

## 已考虑的替代方案

- 修好流式模式（经 `Zip` 回调握手逐条目等待完成）：被否决。fflate 0.8 的 `Zip` 不暴露逐条目完成信号，且故障机理未被充分理解，无法信任据此写的握手逻辑。
- 改用 `bsdtar --format zip`：被否决。GNU tar（Linux CI 默认 `tar`）不能写 zip，脚本将变成平台条件分支。
- 保留流式、外加事后 `unzip -t` 门禁：被否决，那仍建立在产生损坏的代码路径上。

## 后果

- 每次打包都端到端做 CRC 校验；修复后首个产物 `unzip -t` 全部约 1.26 万条目零错误。
- 打包峰值内存几百 MB（条目表 + 归档 + 校验回读），对打包脚本完全可承受。
- 需要继续关注的失败模式只剩用户机器上的解压耗时，不再是归档完整性。
- 验证：重打产物 `unzip -t` 全绿；该产物手工安装完成，12,625 个文件全部落盘。
